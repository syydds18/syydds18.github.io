做工程的人大概都有过这种早晨：打开七八个招标网站，逐个翻公告，担心漏掉一条对口的标。这件事重复、耗时、且完全值得自动化——于是有了 **招标情报系统（BidMonitor-AI）**。

## 目标定义

> 每天早上一张卡片：今天有哪些新标、截止到什么时候、和我们有没有关系。

不追求大而全的爬虫平台，只追求三件事：

1. **源要够**——国家级、省级招标公共服务渠道与多个集团级公开招标渠道；
2. **摘要要短**——AI 把公告压成三句话以内的人话；
3. **推送要准**——只推新增与变更，不制造信息噪音。

## 整体链路

```
采集调度 → 字段结构化 → 去重指纹 → AI 摘要 → 卡片推送
   │            │           │          │          └─ 飞书机器人
   └─ 分源定时   └─ 统一字段  └─ 标题+哈希 └─ 一句话情报
```

### 多源聚合

每个源一个适配器，输出统一结构：

| 字段 | 说明 |
|---|---|
| title | 公告标题 |
| deadline | 投标截止 |
| region | 地区 |
| category | 品类 |
| url | 原文链接 |

适配器只做「取回 + 归一」，任何业务判断都留在下游——这是后期能一口气加源的原因。

### 调度与去重

- **错峰定时**：各源分摊在凌晨时段，失败自动重试，连续失败进告警；
- **去重指纹**：标题清洗后取指纹 + 关键字段哈希，改版重发、置顶重发都不会二次推送。

### AI 摘要

每个新公告交给 LLM 压成一条「情报」：

- 品类、地区、截止时间、体量要点；
- 一句话判断：和工程造价业务相不相关。

摘要失败不阻塞推送——原文标题照发，**可用性优先于聪明**。

## 推送形态

飞书机器人定时吐一张 Markdown 卡片：电站名 + 情报标题 + 摘要 + 原文链接。手机锁屏十秒扫完。

## 一点心得

- 爬虫的难点从来不是「抓到」，而是**三个月后还在正常出数**；
- 摘要模型会错，但漏推一条标更亏——所以设计上宁可多推原文，不可沉默；
- 所有采集仅针对公开发布的招标信息，遵守各平台的访问频率约定。

下一步：把「相关性判断」做成可调的规则 + 模型双通道，减少误报。
